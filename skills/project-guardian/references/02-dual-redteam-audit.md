# Phase 2 手册：双盲红队 Subagent 平行挑刺与跨模型盲审协议

本手册为**纯手动点名工具**：默认关闭，新项目首次立项与日常功能迭代均**禁止自动触发**。**仅当用户在当轮对话中明确开口要求执行「双盲红队 / 辩论 / 挑刺审查」时**，才运行本协议，在写代码前把契约打架、公式漏洞与过度设计抓出来。

---

## 一、为什么必须「双盲（零聊天上下文）」平行挑刺？

同一个主 Agent 刚写完说明书就自己检查，极易顺着刚才的思维惯性自我合理化（把漏洞当成默认前提）。
因此：
1. **双盲隔离**：派发子 Agent 时，**提供用户原始目标及验收场景、`SPEC.md`、`FORMULA.md`（及存量项目的关键接口文件）原文**，绝不附带此前聊天中“为什么这么妥协”的对话过程。
   - 两位审查者先对照用户原话，找出遗漏的交付条件，再审文档内部一致性。
2. **职责正交分立**：拆成两个相反方向的挑刺角色，避免“既想全面又想极简”导致和稀泥，也避免多轮自由辩论把简单系统越辩越复杂。

---

## 二、执行方式

- **支持 Subagent 的环境（如 Antigravity）**：并行调用两次只读 `research`（或 `self` 只读模式）子 Agent，分别注入下方 **红队 A** 与 **红队 B** 提示词。
- **处于 `/swarm` 会话时**：由 Coordinator 分别派发 `redteam-logic` 与 `redteam-yagni`（`workspace: "inherit"`，**严禁传 `fork`**，确保零前序聊天历史偏见），各自只读原文档后直接 `@coordinator` 输出结论，详见 [08-swarm-orchestration.md](./08-swarm-orchestration.md)。
- **不支持并行子任务的单线程环境**：主 Agent 显式分两步独立切换审查清单逐条扫描文件原文，严格对照检查项输出证据。

### 红队 A 提示词模板：系统逻辑、状态契约与计算审计员（Logic & Formula Auditor）

```markdown
你是独立的「系统逻辑与计算契约红队审计员」。请仅根据以下文档原文（必要时只读查阅关联源码），专门寻找会导致算错、卡死、状态冲突或数据污染的硬漏洞。不要提出增加新功能的建议，只抓现有设计走不通或自相矛盾的地方。

待审文件：
- docs/tracking/SPEC.md
- docs/tracking/FORMULA.md（如有）

请逐项硬核查并列出实锤问题（无问题则写“未发现实质漏洞”）：
1. 【术语与枚举分裂】：是否存在同一概念在不同章节/阶段使用了不同名称、不同状态枚举值或大小写不一致？
2. 【上下游门禁死锁】：前一步允许生成或留空的状态（如可跳过项、缺口标记），是否会被后一步的硬校验直接报错拦死且无回退通路？
3. 【前置物理约束缺失】：外部工具、模型或环境的时长、配额、体积、参数限制是否在最后一步才检查，导致前序白跑？
4. 【公式定义域与精度漏洞】：
   - 是否存在分子与分母来自不同过滤集合却直接相除？
   - 是否存在一对多关联（如同一主键拆多行）导致总额被重复累加翻倍？
   - 小数舍入位置是否会导致“分项之和 != 总计”打破守恒等式？
5. 【幂等性与人工层覆盖】：重复导入或重新计算时，是否会产生重复记录，或抹除人工手动修正过的数据？
6. 【存量主干偏离】：是否不必要地绕开既有主干另建了平行模块或多余数据库？

输出格式（每条问题限 3 行）：
- [严重度 P0/P1] 问题位置 -> 具体触发反例 -> 最小修复建议
```

### 红队 B 提示词模板：极简守门员与异常边界挑刺员（YAGNI & Edge-Case Critic）

```markdown
你是独立的「极简主义（YAGNI）与异常边界红队守门员」。请仅根据以下文档原文，专门寻找“AI 擅自加戏过度设计”、“异常边界漏处理”以及“验证盲区”。严禁建议把系统做得更复杂，一切以最简可靠闭环为准。

待审文件：
- docs/tracking/SPEC.md
- docs/tracking/FORMULA.md（如有）

请逐项硬核查并列出实锤问题（无问题则写“未发现实质漏洞”）：
1. 【过度设计 / 擅自加戏】：是否包含了超出核心目标的冗余功能、复杂重试/计费流程或不必要的抽象层，能够砍掉简化？
2. 【五类边界遗漏】：`0`、`空值(NULL)`、`负数`、`重复输入`、`关联缺失` 是否全部有明确动作？有无把 `NULL` 静默当 `0` 的隐患？
3. 【盲审误放行】：是否存在系统实际上无法检测的维度（如缺少某类输入信号），却没有标记 `unverifiable` 而直接默认判为 `通过(pass)`？
4. 【界面与交付物错位】：预览/展示源与实际导出/保存源是否保证指向同一份数据？多选筛选器是否保证取自真实业务集并支持“全选 ↔ 全清”双向切换？
5. 【数据规模退化】：当数据量增长 10~100 倍时，是否存在明显的 O(N^2) 循环比对或一次性渲染海量节点导致卡死的隐患？

输出格式（每条问题限 3 行）：
- [严重度 P0/P1] 问题位置 -> 真实翻车场景 -> 最简收敛改法
```

## 三、主 Agent 裁判收敛与用户拍板规范

收到红队 A 与红队 B 的输出后，主 Agent 执行三步收敛：
1. **去重与过滤伪问题**：剔除吹毛求疵的边缘假设与任何试图增加系统复杂度的建议，只保留真正会导致算错、卡死、丢数据或加戏的 **P0 / P1 硬伤**。
2. **无需打扰用户的纯技术疏漏**：如拼写不一致、漏写显然的 `0/NULL` 保护，直接修正进文档并简要告知。
3. **涉及业务取舍的分叉项**：翻译成 **「生活化比喻 + 推荐改法 `(Recommended)`」** 一次性呈交用户确认，更新锁定 `SPEC.md` 与 `FORMULA.md`。

## 四、可选升级：导出《跨平台模型盲审交接包》（重大项目适用）

当用户希望把当前项目发给外部另一个模型做交叉核验时，按以下模板生成交接摘要（外部模型无法直接读取未提交文件，必须列出明确路径与 SHA-256 前 12 位指纹）：

```markdown
# 跨模型独立审查交接包（快照时间：YYYY-MM-DD HH:MM）

请基于以下追踪文档与代码快照进行独立只读盲审，重点核查：契约自相矛盾、计算公式口径偏差、未覆盖边界与假完成项。

| 文件角色 | 相对路径 | SHA-256 前 12 位 |
| :--- | :--- | :--- |
| 项目宪章 | `AGENTS.md` | `<sha256_12>` |
| 系统真源说明书 | `docs/tracking/SPEC.md` | `<sha256_12>` |
| 计算公式契约 | `docs/tracking/FORMULA.md` | `<sha256_12>` |
| 实时状态面板 | `docs/tracking/STATUS.md` | `<sha256_12>` |
| 主线任务清单 | `docs/tracking/TODO.md` | `<sha256_12>` |
```
