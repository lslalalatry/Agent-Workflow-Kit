# 提交与上传前的 AI 代码审查

当用户准备提交或上传时，由当前 Codex 或 Antigravity 对话实际审查。Git 钩子只核对审查记录与代码版本。日常修改过程中可以继续工作，提交和上传沿用项目已有授权。

1. 确认本次要交付的目标和文件，只暂存相应改动。在仓库根目录运行 `python3 "<技能目录>/scripts/code_review.py" show`。保存首行的 `scope`，实读后续完整差异、相关调用方及已有测试。遇到二进制文件或子模块，打开对应产物或提交检查。纯文档变更只核对事实、示例和链接。
2. 先看改动会不会破坏默认入口、旧数据、失败重试或并发写入。再看是否复制了已有业务规则、留下未用分支、增加不需要的依赖或绕行入口。指出具体位置、触发场景、后果和最小修复。格式偏好可以单列为建议。
3. 发现会造成错误结果、数据损失或让同一规则必须多处维护的问题时，先修复并跑相关验证。重新暂存后再次 `show`，检查最终改动。缺少足以判断关键风险的证据时，告知具体阻塞。
4. 审完后运行 `python3 "<技能目录>/scripts/code_review.py" record --scope "<本轮实读的 scope>" --summary "<实查位置、发现及修正、验证结果>"`。只为实际审完且无阻断项的版本登记。暂存内容或基线变化时，原记录自动失效。记录保存在本地 Git 元数据中。
5. 推送时，钩子按目标引用逐个核对待上传的提交。遇到缺记录的提交，用 `show --commit <提交号>` 实读，再用 `record --commit <提交号>` 与同样的两个参数补记。相同差异沿用已有记录。创建远端新分支或标签时会检查它可达的历史。换电脑后可按提示补审。若要通过其他渠道上传代码，AI 还须核对交付文件与已审版本相符。

例如，两个页面各自复制了退款过滤条件，当前样例都通过。评审应指出哪两个调用方会在下次改口径时产生不同结果，复用现有计算入口，并验证两个页面。摘要中写明改了哪里、怎样验证。Git 只能核对版本和记录，审查质量来自 AI 对改动的实际判断。

审查方法借鉴了 ECC 的差异优先和按影响报告问题。[ECC 代码审查说明](https://github.com/affaan-m/ECC/blob/main/agents/code-reviewer.md)
