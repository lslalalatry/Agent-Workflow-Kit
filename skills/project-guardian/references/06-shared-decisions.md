# 共享决定与 Git 交接

同一项目的各个对话从项目文件取得当前口径。收到用户明确拍板的对话负责在本轮写回。草案和推测保持待确认。用户修订旧规则时，保留旧决定，并标明新决定取代或补充的编号。只有两条指令实质冲突且取代关系仍不清楚时，才向用户确认。

## 动手前读工作区

1. 新对话、旧对话恢复工作、继续实现或开始编辑共享文档时，定位实际仓库根目录和分支，检查已暂存、未暂存及未跟踪的相关改动。读取当下的 DECISIONS、STATUS、TODO 及受影响的 SPEC、FORMULA。确认和当前任务有关的待实现决定与已验收行为。用户对旧聊天说「继续」，也执行这一步。
2. 当项目包含多个架构文档或大量决定条目时，先用 `python3 "<技能目录>/scripts/query_docs.py" search --root "<项目根目录>" --query "<关键词>"` 定位相关 `D-编号`、`F-编号`、术语和模块设计卡，再按返回路径用 `read` 子命令只读命中章节，避免一次整包塞入上下文。引用既有规则或参数时，必须核对并逐字摘录原文件里的 `D-编号`/`F-编号` 与准确数值，**严禁凭长对话压缩后的模糊记忆猜阈值或规则口径**。
3. 多对话维护同一份追踪文件时，用随技能安装的 `scripts/chat_sync.py` 读写。同一工作目录下，两个对话可以读取对方尚未提交的决定。其他工作副本先在交接时核对同步状态，只在可安全整合时继续。拿不到对方本地改动时，说明最后可确认的版本。
4. 只读用 `python3 "<技能目录>/scripts/chat_sync.py" read --root "<项目根目录>"`。准备修改时，给这次读取一个独立、位于仓库外的空临时目录，追加 `--draft "<草稿目录>"`。从该草稿中**实读内容**，保留其他对话或用户的原文，再编辑相关段落。开始实现前和准备交接前如发现涉及本任务的规则已变化，按最新决定核对自己的实现。

## 拍板当轮写回

在草稿的 DECISIONS.md 写明新编号、拍板日期、规则、原因（如已知）、取代或补充关系及影响范围。首个决定遇到尚无 DECISIONS.md 的旧项目，可在草稿中新建。多对话项目初始化时启用 `--with-decisions`。同一拍板重复送达时沿用已登记的编号。

| 决定影响 | 同一轮更新 |
| --- | --- |
| 用户可见的行为或业务范围 | 更新 SPEC 对应条目，区分已批准目标和当前已上线行为。 |
| 公式、数据范围、统计规则 | 更新 FORMULA 的定义及样例。尚待切换的规则标为「已批准，待实现」。保留当前已运行的观察契约，切换实现时再启用新契约并实测。 |
| 后续工作、验收或已失效任务 | 调整 TODO 的依赖、期望值及状态。新口径的实现或验收保持待办或候选。 |
| 主线、阻塞或交接动作 | 更新 STATUS 的断点、实际结果和下一步。 |
| 暂缓事项或归档记录 | 按影响更新 BACKLOG。 |

每个实际有变化的条目带上同一决策编号。例如本轮新增 D-018，修改以上三份业务文档后，运行：

```sh
python3 "<技能目录>/scripts/chat_sync.py" apply --root "<项目根目录>" --draft "<草稿目录>" --decision D-018 --affects TODO.md SPEC.md FORMULA.md
```

按实际影响列文件。只涉及决策账本时省略 `--affects`。普通进度修改用 `apply --root … --draft …`。工具会核对读取后的文件内容、Git 分支和版本，串行写入该工作目录。遇到草稿过期，使用新草稿重读，把仍适用的改动合入最新版，重新检查决定编号和引用。运行后再核对工作区差异；同一批决策及其受影响文档一起存档。提交检查会核对暂存版本中的决策引用。文件内容的业务含义由本轮对话核实。

## 仓库与提醒

提交或上传前完成[AI 代码审查](./07-code-review.md)。提交检查暂存内容，推送检查本次上传的提交。

先核对已有 Git 仓库、远端名称、上游分支是否对应本项目。项目更新沿用现有 GitHub 仓库。本地尚未配置远端时，也先在用户指定的账号或组织核对已有仓库的用途。多个远端时核对目标分支实际跟踪的仓库。首次需要远端且确无可复用仓库时，确认或沿用已明确的账号、仓库名、可见性和建仓授权。仅本地协作可以持续使用现有工作目录。

- **本地存档**。确认为一次完整的决策变更、通过阶段验收或准备换人交接时，检查本次差异与暂存区。已有针对本项目的 commit 授权时，检查通过后只提交本次范围。否则告知哪组变更尚待 commit。若其他人的修改已暂存，先分清提交范围。
- **远端交接**。跨设备、团队取用、里程碑交付时检查当前分支和上游。可用 `git status --short --branch`、`git remote` 和 `git rev-list --left-right --count HEAD...@{upstream}` 了解本地状态与最近已知的领先、落后数量。需要判断远端现状时先刷新对应远端引用；无法刷新则指明依据是本地缓存。上游不存在时，如实报告。出现分叉时保留双方提交并先处理冲突。已有针对正确远端和分支的 push 授权时才推送，成功后核对远端分支指向。commit 与 push 分别判断授权。
- **提醒频率**。在交接节点报告本地待存档内容、已提交待推送数量或具体阻塞。已同步就结束；同一节点状态相同只提醒一次。项目文件、账号登录、工具可用和历史无关项目的许可都不能代替当前授权。

## 子模块闭环、主线推送策略与增减功能规程

### 1. 一子模块一 `.md` 与完结换窗信号
- 当项目启用 `docs/architecture/modules/` 时，每个独立子模块或子功能维护一份独立设计卡（复制 `modules/_TEMPLATE.md`）。单窗口原则上只聚焦闭环 **1 个子模块**。
- **主动提示可以新开对话框**：当当前子模块的全部待办验收通过、`verify_guardrails.py` 绿灯且本地工作区已干净同步后，AI 必须在回复末尾主动给出明确信号与下一窗口开场口令：
  > **🟢 本任务已完结（可新开对话框）**：说明 `main` 同步状态与提交号，并附一句可直接复制的新窗口继续指令（如 *“重读工作区状态与下一个 `modules/<name>.md`，开始下一任务”*）。

### 2. 主线推送策略（读取根目录 `AGENTS.md` 第 6 节 `delivery_mode`）
| `delivery_mode` 配置值 | 行为模式 | 硬前置安全锁（缺一不可） |
| :--- | :--- | :--- |
| `auto_push_main_when_clean`（用户显式开启） | 子模块验收完结后，AI 自动提交、合回并推送 `<主分支>`，并核对远端最新 SHA 与工作区干净，随后提示“可以新开对话框” | ① 相关测试全绿；② `verify_guardrails.py` 绿灯；③ `code_review.py` 已登记实读差异结论；④ `git pull --rebase origin <主分支>` 无冲突且已配 `origin`；⑤ 不涉及删库/生产线上发布等额外高危动作。任一条件不满足立即停下报告阻塞。 |
| `prompt_push_on_done`（默认模式） | 每次任务完结或到达交接节点，AI **必须输出醒目的「📦 交付与主线同步提醒卡」**，列明未提交文件数与领先 `origin/<主分支>` 提交数，主动询问是否立即审查并推送 `<主分支>` | 收到用户确认后按 `07-code-review.md` 完成审查、提交与推送，并给出可新开对话框信号。 |

### 3. 增加功能与减少功能标准处理动作
- **增加功能（Scope Addition · 先登记，不抢跑）**：
  - 若当前正在推进的子模块尚未完结推上 `main`，AI 默认**不把新需求直接揉进当前改动**，而是先登记至 `docs/architecture/DRAFT.md` 或 `docs/tracking/BACKLOG.md`（或新建独立 `modules/<new_feature>.md`），主动建议：*“已登记新需求，先把眼前模块验完推送 `main`，再新开对话框专门做这项新增功能。”* 仅当用户明确要求插队暂停当前任务时才切换。
- **减少 / 砍掉功能（Scope Reduction · 四步软下线）**：
  1. **锁决策**：在 `DECISIONS.md` 登记新 `D-编号` 写明砍掉或停用范围，将对应 `modules/<feature>.md` 标为 `deprecated`（防后续新窗口按旧文档复活）。
  2. **拆清理**：列出受影响的入口、路由、定时任务与死代码，拆成微任务清干净，不留半截僵尸代码。
  3. **保数据**：区分“代码与定时停用”和“历史数据保留只读”（严禁因砍功能误删历史审计资产）；若仅本期暂缓，则整块移入 `BACKLOG.md` 上半区暂缓池。
  4. **验并推**：跑通剩余全量测试，审查提交并推送 `main` 后提示新开对话框。

### 4. 多任务真并行防撞规则（含 `/swarm` 模式）
- 两个对话窗口严禁同时修改同一个文件或同一张 `modules/*.md`。
- 当用户主动开启 `/swarm` 进行多工匠并行开发时，严格执行 [08-swarm-orchestration.md](./08-swarm-orchestration.md)：由 **Coordinator 独占修改 `docs/tracking/` 总账本**，Author 通过 `workspace: "share"` 在各自 **`swarm/<worker>`** 分支独立开发并只更新对应 `modules/<module>.md`，合回主干且删光临时分支与 worktree 后再统一审查、验收并推送 `main`。
- 非 `/swarm` 的普通并行场景必须使用独立 `git worktree` 或 `exp/<module>` 隔离分支；**先完成者先 `fetch + rebase origin/<主分支>` 合回并推 `main`，并当场删除自己的临时分支/`worktree`**（严禁长期挂着不合入）。
