# Phase 1 手册：需求挖掘（`/grill-me`）、比喻化沟通与计算公式契约

本手册仅用于**新项目立项**或**目标边界尚不明确的跨模块重大改造**。若用户已给出明确规则或属于常规简单功能修改，禁止启动多轮访谈与外部项目调研，直接核对受影响契约（涉计算同步更新 `FORMULA.md`）并快速执行。

---

## 定稿前借鉴已有方案

新项目或重要新能力收到用户初步想法后，先摘录原始目标和交付场景。查现有仓库已经解决了哪部分，再按用途和约束搜索 GitHub 同类项目。带着实例进入 /grill-me，业务取舍由用户决定。明确的小修直接使用现有实现。

优先打开领域内星数较高、近期有实质维护的候选。记录查询日期、星数及最近一项相关功能、缺陷修复或发布的日期和链接。区分实际改动与机器人更新时间。实读核心实现、测试或使用示例。通常比较最相关的两三个；小众领域如实说明找到的候选和局限。

向用户说明每个候选已经解决什么、可借鉴哪项设计、与当前约束的差距。比较直接复用、少量适配、只借鉴思路和自行实现的代价。引入代码或依赖前核对许可证、兼容性与维护负担。在 SPEC.md 保留选中的做法、来源与理由。外部搜索不可用时标记未核实，继续可开展的本地盘点。

本流程借鉴 ECC 的 search-first，按需采用其调研方法。[ECC 官方工作流](https://github.com/affaan-m/ECC/blob/main/skills/search-first/SKILL.md)

## 一、深度挖掘五步法（先自查，后单问）

1. **先查现有仓库与已有基础设施，不问能自己查到的事实**
   - 若为存量项目，必须先自主阅读目录结构、入口文件、配置与现有测试，摸清既有主干链路（防止后续另起炉灶）。
   - 若新项目涉及系统架构、数据库或图片/文件存储，**同步读取 [01a-architecture-blueprint.md](./01a-architecture-blueprint.md)**：先盘点本地或既有云端是否已有可用数据库（优先考虑同集群分 Schema 集中存储），再按八大架构支柱对齐技术选型、媒体存储、权限模型、接口多态与部署回滚，未拍板方案先记入 `docs/architecture/DRAFT.md`。
2. **梳理决策依赖树，每次只问 1 个核心问题**
   - 按“上游决定下游”的顺序提问：先定**目标边界与主干复用** → 再定**数据/公式口径** → 再定**外部工具与异常回退** → 最后定**交付形态**。
   - 前一题未定前，不抛出依赖它的下游细节问题。
3. **强制使用「生活化比喻 + 后果对比 + 首选推荐」话术结构**
   - 严禁直接问用户：*“是否采用幂等 Upsert 还是 Append-only 配合视图聚合？”*
   - 必须转化为：
     - **比喻画面**：*“就像每月往账本里贴发票：方案 A（推荐）是同一张发票重贴时自动替换旧的，账本永远不会算重；方案 B 是每次贴在最后保留痕迹，但查询稍慢。”*
     - **直白后果**：说明对速度、准确性、后续维护的实际影响。
     - **明确推荐**：第一项固定标注 `(Recommended)` 并给出简短理由。
4. **必查的五大高危盲区（AI 最容易脑补翻车处）**
   - **盲区 1 · 既有主干边界**：存量改造是在原页面/原服务上直接升级，还是允许新建入口？（默认必须在原主干演进）。
   - **盲区 2 · 外部工具与数据源归属**：每一步具体调用哪个工具/CLI/接口？调用前必须先用 `--help` 实读确认参数。
   - **盲区 3 · 失败后的处理责任**：某步校验不通过时，是系统内自动重跑，还是停下让用户在外部处理后重新上传？（**严禁擅自加戏设计复杂的站内重试/计费系统**）。
   - **盲区 4 · 人工修正的持久性**：是否存在人工手动调整或特批的数据？重新导入或重算时如何保证人工结果不被冲掉？
   - **盲区 5 · 五类边界值处理**：遇到 `0`、`空值(NULL)`、`负数`、`同键重复行`、`匹配不上` 时，系统应该报错阻断、留空提醒还是跳过？

## 二、计算公式契约锁（`FORMULA.md` 强制触发与编写规范）

### 2.1 触发条件
只要项目包含以下任一内容，**必须启用并填写 `docs/tracking/FORMULA.md`**，不得只把公式散落在 `SPEC.md` 自然段里：
- 金额、成本、税费、汇率、折扣、利润或对账汇总；
- 比率、均值（特别是加权均值 vs 算术均值）、份额占比、同比/环比增速；
- 评分权重、排序打分、阈值分级或置信度计算；
- 几何尺寸、物理量换算、时间窗对齐或配额预算分配。

### 2.2 每条公式必填的「七要素」硬检表

编写每条公式卡 `[F-XX]` 时，逐项核对：
1. **唯一英文 ID**：全仓唯一标识（如 `weighted_unit_price`），代码注释与测试直接引用该 ID。
2. **业务定义**：用一句主动句定性，明确区分易混淆概念（例如区分“成交加权均价”与“目录简单算术均价”）。
3. **精确表达式**：写出无歧义数学式或伪代码，禁止使用“大概按比例分摊”之类模糊描述。
4. **分子与分母同源过滤池（极高危！）**：
   - 明确写出分子纳入哪些记录、分母纳入哪些记录；
   - **铁律**：除非用户书面特批并说明业务含义，**严禁将过滤条件不同的两个样本池直接相除或相减**。
5. **精度与舍入位置**：
   - 明确中间过程用整数最小单位（如乘 100 化分）还是高精度十进制，严禁二进制浮点数直接累加比较；
   - 明确**在哪一步舍入**（逐行舍入后再求和，还是精确求和后最后一步舍入），并写明由此产生的尾差如何处理。
6. **五类边界行为**：逐一写死 `0`、`NULL`、`负数`、`同键拆多行（一对多）`、`缺关联项` 时的精确输出（如分母为 `0` 必须返回 `NULL` 显示 `—`，禁返 `0` 或 `NaN`）。
7. **守恒不变量与 3 组手算黄金样例**：
   - 写出至少 1 条系统自动自检的守恒等式（如 `INV-01: Σ各子类小计 == 总计原值，容差 <= 0.01`）；
   - 手工算出 **正常例、零/空边界例、易错反例（如一对多拆行防翻倍、临界小数舍入）** 共 3 组确定数字，后续直接写入单元测试断言。
