# 通用项目架构设计蓝图（Phase 1 架构扩展手册）

本手册为 `project-guardian` 的**通用架构设计模块**。当用户开启新项目或做系统级重构、且希望在动手写代码前搭好完整技术框架时，主 Agent 按本手册**先盘点存量基础设施，再用生活化比喻逐项对齐八大通用架构支柱**，产出可独立维护的模块化架构文档 `docs/architecture/`（及部署骨架 `deploy/`），同时保持根目录 `AGENTS.md` 与 `docs/tracking/` 轻量化不膨胀。

> **适用原则（YAGNI）**：
> - 纯问答、单点修复、小脚本工具：跳过本手册，走极简快车道。
> - 中大型系统、多模块应用、含数据库/媒体存储/权限/部署的项目：初始化时启用 `--with-architecture`（或按需补建 `docs/architecture/`），开干前先对齐八大支柱。

---

## 一、开局第 0 步：先盘点存量基础设施，再画新图纸

在推荐任何数据库、对象存储、缓存或服务器拓扑前，必须**先实查当前环境与既有资产**（严禁凭空另起炉灶）：
1. **查已有数据库与服务器**：检查本地工作区、同账号既有项目配置或用户声明的云端基础设施，搞清是否已有运行中的 PostgreSQL / MySQL / DuckDB / SQLite / Redis。
2. **集中存储判定法则**：
   - **能共用同集群分 Schema，就绝不新开物理库**：若已有成熟关系型数据库集群且同属一个信任域，优先在该集群内新建独立 Schema（如 `app_a.*`、`core.*`）并复用公共字典/主数据，避免日后跨库关联难、维护多套备份。
   - **必须物理隔离的唯一理由**：不同安全合规域、高吞吐写入互相拖垮、或明确面向外部独立交付时，才独立建库，并写明与已有库的数据边界及单向同步方式。
3. **写回 `docs/architecture/ARCHITECTURE.md` 第 1 节「存量资产盘点与复用决策」**，明确哪些复用、哪些隔离、哪些冻结不动。

## 二、通用项目架构八大支柱清单

所有架构设计必须逐项核对以下 8 个通用维度；不涉及的维度显式标注 `不适用（原因）`，禁止留白或含糊跳过：

| 支柱 | 目标文档 | 核心必答问题（设计时必须给出明确落地方案） |
| :--- | :--- | :--- |
| **1. 存量盘点与系统拓扑** | `ARCHITECTURE.md` | 复用哪些现有服务/库？系统分为哪几层（接入/服务/异步 Worker/存储/外部集成）？主干入口与端口是什么？ |
| **2. 数据集中存储与粒度契约** | `DATA_MODEL.md` | **OLTP（事务写入）与 OLAP（多维分析）是否分离？** Schema 如何划分？每张核心表的业务粒度、唯一幂等键、状态机流转是什么？人工修正数据如何与自动重算层物理隔离？ |
| **3. 图片与富媒体存储** | `ARCHITECTURE.md` + `DATA_MODEL.md` | **严禁业务图片进 Git、严禁无上限堆本地系统盘、严禁长期只存第三方易失效外链。** 二进制文件存哪类对象存储（OSS/COS/S3/R2）？是否按 SHA-256 内容寻址去重？元数据表存哪些字段？私有预览（短时效预签名 + 缩略图）与公开外联（如邮件配图独立只读前缀）如何隔离？ |
| **4. 业务术语与跨模块边界** | `README.md` / `SPEC.md` | 全仓唯一术语表与封闭枚举值是什么？超复杂多模块时，是否需要按子域拆入 `docs/architecture/modules/<module>.md`？ |
| **5. 权限模型与凭据安全** | `SECURITY_AND_AUTH.md` | 角色与资源操作矩阵（RBAC）是什么？多租户/成员数据如何做行级隔离？未登录默认拒绝策略是什么？密钥、Token、Cookie 存在哪，如何保证不进前端、Git、日志或截图？ |
| **6. 接口契约与前端多态清单** | `API_AND_UI_STATES.md` | 统一响应/分页/错误码结构是什么？列表与详情组件必须显式覆盖哪五态：**加载中（Loading）、真实空（Empty）、真实零（Zero）、部分失败/不可验证（Partial/Unverifiable）、无权限（Forbidden）**？ |
| **7. 草稿缓冲与正式晋升** | `DRAFT.md` | 未拍板的架构猜想、多方案对比、待调研外部 API 统一放入 `DRAFT.md`，确认后再晋升进 `SPEC.md`、`DATA_MODEL.md` 与 `TODO.md`；禁止把未定稿猜想混进正式规格。 |
| **8. 环境、QA 部署与回滚** | `DEPLOYMENT_AND_QA.md` + `deploy/` | 本地 / 测试（QA）/ 生产三套环境配置契约（`.env.example`）差异是什么？部署与迁移是否幂等？备份是否经过**真实隔离还原演练**？一键回滚命令是什么？ |

## 三、关键选型通俗沟通模板（供 Phase 1 访谈直接复用）

向非技术或跨领域用户对齐架构选型时，必须先用生活化比喻讲清后果再推荐：

### 模板 A · 集中存储选型（同库分 Schema vs 独立物理库）
- **比喻**：就像公司扩业务，**方案 A（推荐）** 是在现有大楼里新隔一间办公室（同数据库集群建新 Schema），水电保安和总台通讯录现成复用，各部门账本互相能对上；**方案 B** 是单独盖一栋新楼（独立建库），物理绝对隔离，但以后想把两个部门数据放一张表里算总账，得每天雇卡车倒腾。
- **主推荐**：优先同库新 Schema；仅当隔离合规或高并发互抢资源时再拆物理库。

### 模板 B · 图片与文件存储（对象存储 + 数据库索引 vs 本地磁盘 / 外链）
- **比喻**：**千万别把所有商品照片直接贴进账本里（存数据库 BLOB），也别只记一张别人家网址的便条（第三方 CDN 链接过几天就 403 失效），更别全塞进收银台抽屉（服务器本地盘早晚爆满）。**
- **标准做法（推荐）**：照片本体放专业仓库（对象存储 OSS / COS / R2），按文件指纹（SHA-256）去重做到“同一张图全公司只存一份”；数据库里只记一张 `media_assets` 资产目录卡片（编号、仓库地址、来源是否失效、尺寸/视觉指纹、保留期限）。

### 模板 C · 草稿缓冲（`DRAFT.md` vs 直接写入 `TODO.md`）
- **比喻**：`DRAFT.md` 是设计师手里的**速写本**，随便涂改对比；`SPEC.md` 与 `TODO.md` 是贴在工地墙上的**施工蓝图与派工单**。未拍板前只改速写本，拍板后再往正式蓝图抄，工人才不会拆了重砌。

## 四、与 `project-guardian` 控制面的职责边界

| 层级 | 目录位置 | 谁来管、何时读 | 核心铁律 |
| :--- | :--- | :--- | :--- |
| **常驻薄宪章** | `AGENTS.md` | 每轮必读（`<= 20KB`） | 只写红线、项目配置卡与入口索引，不写大段业务架构 |
| **轻量状态控制面** | `docs/tracking/` | `STATUS.md` 每轮必读；`verify_guardrails.py` 机械守门 | 管进度、拍板台账（`DECISIONS.md`）、公式契约（`FORMULA.md`）与证据验收 |
| **分域架构知识库** | `docs/architecture/` | 立项设计或修改对应模块时按需实读（兼容 Obsidian） | 管系统全景、集中数据库、图片存储、权限、UI 五态与部署运维，避免单文件膨胀 |
| **部署编排目录** | `deploy/` | 构建、QA、发布与回滚时实读实测 | 放 Compose/容器/环境变量模板/备份回滚脚本，**严禁存入明文密钥** |
